## Context

См. [proposal.md](proposal.md) и [спецификацию](specs/research-wiki/spec.md). Сейчас сайт отсутствует; `docs/README.md` уже служит короткой wiki и точкой входа для агентов, а `docs/research.md`, `docs/model-research.md`, `docs/tau-bench-review.md`, `docs/team.md`, `docs/vkr.md` и `docs/agents/workflow.md` содержат подробности. В проекте нет веб-стека, remote и решения о публикации. Существующие правки в `docs/` и новые файлы других задач нужно сохранить.

## Goals / Non-Goals

**Goals:** локальная статическая wiki из тех же Markdown-файлов; короткий маршрут для человека и полный для агента; проверяемая навигация и ссылки.

**Non-Goals:** сервер, авторизация, CMS, автоматическое извлечение фактов из длинных файлов, размещение сайта и смена канонического места проектных решений.

## Decisions

### 1. Генератор — Material for MkDocs

Добавить `mkdocs.yml` и зафиксированную зависимость для сборки документации. Material уже даёт тёмную палитру, левую навигацию, правое оглавление и клиентский поиск с языками `ru` и `en`; для этих функций не нужны собственные HTML, JavaScript и сервер. Поиск работает на статическом сайте. Альтернатива — вручную собранная страница — потребовала бы отдельного индекса поиска, обработки Markdown и адаптивной навигации. Docusaurus добавил бы JavaScript-сборку и лишний стек.

Опорные сведения: [навигация Material](https://squidfunk.github.io/mkdocs-material/setup/setting-up-navigation/), [поиск](https://squidfunk.github.io/mkdocs-material/plugins/search/), [локальная сборка MkDocs](https://www.mkdocs.org/user-guide/cli/). Использовать обычную боковую навигацию без `navigation.instant`, которому нужен `site_url`; адрес публикации пока неизвестен.

### 2. Сохранить `docs/README.md` главной страницей

MkDocs отображает единственный `docs/README.md` как корневой `index.html`; добавлять рядом `docs/index.md` нельзя, иначе `README.md` не попадёт в сайт ([правило MkDocs](https://www.mkdocs.org/user-guide/writing-your-docs/#index-pages)). Существующий краткий перечень подтверждённых решений и ближайших задач остаётся здесь. При необходимости его сокращают и снабжают ссылками на канонические разделы, не копируя подробные таблицы. Фразу о ненужности генератора сайта в правилах wiki обновить при внедрении.

Добавить `docs/research-overview.md` как короткую карту вопроса, стенда и сравнения; `docs/sources.md` — как отдельный реестр научных статей. В `mkdocs.yml` задать явный порядок: «Начало» (`README.md`), «Исследование» (краткий обзор и источники), «Подробные материалы» (постановка, модели, τ-bench), «Работа над ВКР» (команда, требования, процесс агента). Все текущие документы из `docs/` перечислить в меню.

### 3. Ссылки и исходные документы

Оставить относительные ссылки между Markdown-файлами: MkDocs преобразует их в ссылки сайта, а в репозитории они остаются читаемыми. Две ссылки из `docs/README.md` и `docs/agents/workflow.md` на корневой `AGENTS.md` ведут за пределы `docs/` и мешают строгой проверке. Заменить их на текстовый путь `AGENTS.md` с переходом к доступному в сайте `docs/agents/workflow.md`; ссылка на сам `AGENTS.md` остаётся в корневом `README.md` для работы из репозитория. Не копировать агентские правила внутрь сайта.

### 4. Научные источники — ручной короткий реестр

Перенести на `docs/sources.md` не сами статьи, а библиографические записи и объяснение их роли. Начальный набор берётся из уже проверенных ссылок `docs/research.md` и `docs/tau-bench-review.md`: τ-bench, τ²-bench, τ-Knowledge, HAL, SABER и работа Liu о System One. При заполнении сверить первичную страницу каждой записи, не выводить статус рецензирования из упоминания в обзоре. Для карточок моделей и документации поставщиков дать отдельный указатель на подробный обзор; не смешивать их со статьями. Численные результаты из публикаций не выдавать за наши.

### 5. Проверка и обслуживание

Сборка `mkdocs build --strict` должна завершаться без предупреждений о навигации и внутренних ссылках; проверку якорей включить явно. Генерируемый `site/` исключить из Git. Команды установки, локального просмотра (`mkdocs serve`) и сборки записать в корневом `README.md`. После сборки вручную проверить главную, длинную страницу, поиск «ВКР»/«KEV», переход по оглавлению, узкий экран и фокус клавиатуры. Внешние ссылки на статьи проверить по первичным страницам при создании реестра: строгая сборка не проверяет доступность внешних сайтов.

## Risks / Trade-offs

- Краткие страницы могут отстать от подробных документов → держать в них только состояние и ссылки, а при изменении решений проверять обе страницы по правилам wiki.
- Строгая сборка обнаружит уже существующие ссылки за пределы `docs/` или некорректные якоря → исправить только затронутые маршруты, сохранив прямые пути к Markdown для агентов.
- Поиск по смешанному русскому и английскому тексту может по-разному обрабатывать формы слов → указать `ru` и `en` и проверить реальные запросы из спецификации.
- Новая зависимость усложнит локальную сборку → закрепить её версию и не добавлять плагины, пока стандартных возможностей достаточно.

## Migration Plan

Добавить конфигурацию и короткие страницы рядом с текущими Markdown, затем поправить ссылки и выполнить строгую сборку с визуальной проверкой. Существующие длинные документы остаются на прежних путях. При отказе от веб-представления удалить конфигурацию сборки и новые обзорные страницы; исходная wiki продолжит работать как Markdown.
